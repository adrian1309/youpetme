# Scaffold Backend Module

Generate the folder and file skeleton for a new business module under `apps/api/src/modules/<module>/`, matching the `iam` module's structure exactly (ARCH-001, AGENTS.md — Repository structure).

## Before scaffolding

1. Confirm the module is one already named in ARCH-001's module list (`iam`, `animals`, `adoptions`, `shelters`, `ai`, plus cross-cutting `notifications`/`platform`) or has been explicitly approved as a new module — do not invent a module name or scope on your own (AGENTS.md — When uncertain).
2. Confirm a corresponding User Story / Use Case / Technical Specification exists or is in progress for at least the first slice of this module — per AGENTS.md's Development Rule, no production functionality is implemented before its User Story and Use Cases are approved. Scaffolding empty structure ahead of that is fine; implementing behaviour is not.

## Structure to generate

```text
apps/api/src/modules/<module>/
├── domain/
│   ├── entities/
│   ├── value-objects/
│   ├── events/
│   └── ports/
├── application/
│   ├── use-cases/
│   ├── commands/
│   └── dto/
├── infrastructure/
│   ├── persistence/prisma/
│   ├── security/          # only if the module needs it — omit otherwise
│   └── events/
├── presentation/
│   └── http/
└── <module>.module.ts
```

Only create the specific subfolders/files actually needed for the module's current scope — do not pre-create empty placeholder files with no content or purpose just to match the shape exactly. `security/` in particular is IAM-specific; most other modules will not need it.

## Rules while scaffolding

- **Dependency direction is non-negotiable** (AGENTS.md — Architecture rules): `presentation → application → domain`, `infrastructure → application/domain ports`. Domain code must not import NestJS, Prisma, HTTP, or any concrete infrastructure provider.
- Prisma-specific code belongs only under `infrastructure/persistence/prisma/` — never in `domain/` or `application/`, and never in `packages/contracts`.
- `packages/contracts` may need new transport types for this module's public API — add them there, not inside the module itself, and keep them limited to transport (request/response/error shapes), never domain entities or Prisma types.
- REST endpoints under `presentation/http/` use the `/api/v1` prefix (ARCH-001).
- New endpoints must be reflected in the OpenAPI document generated by the API (ARCH-002) — do not write a parallel hand-maintained API description.

## Test scaffolding (per ADR-013, TDD is mandatory)

Do not write implementation before the corresponding test, per AGENTS.md — Test-Driven Development is mandatory. When scaffolding:

- Unit test files (`.spec.ts`) are co-located with the domain/application code they will test.
- Integration test files (`.integration-spec.ts`) are co-located with the infrastructure adapter they will test.
- E2E tests for this module's flows go in `apps/api/test/`, not inside the module folder.

## After scaffolding

1. Register the new module in the NestJS root application module.
2. If this module introduces a genuinely new architectural decision (not already covered by an existing ADR), flag it rather than deciding silently — see the `create-adr` skill.
3. Note in the end-of-story summary (AGENTS.md) that a new module was scaffolded and what its current scope covers, since this is a structural change worth surfacing even if small.
